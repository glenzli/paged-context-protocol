# 维护审阅升级与预算

状态：2026-09-09 已实现，已更新本地 Runtime 与 Console 并检查实际设置页。已确认采用准入阈值，先启用本地 Sol；Astra 命名部署尚未配置，保持关闭。不改变 PCP 0.8 协议。

## 目标与预算

让 Sol High 成为常规复核层，让少量 Astra Low 处理剩余实质分歧。预算用于阻止异常循环，不限制正常维护到每天几十项。模型更强不等于来源完整，也不等于自动取得应用权限。

| 层级 | 职责 | 滚动 24 小时默认限制 |
| --- | --- | --- |
| Luna | 候选生成、普通初审、明确无增量的淘汰 | 沿用现有维护调度限制 |
| Sol High | 不确定项、旧主题刷新、可修复的来源/语义问题 | 300 次模型调用，6,000,000 总 token，任一耗尽即暂停该层 |
| Astra Low | Sol 后仍有可裁决分歧或较高信息丢失风险 | 10 次模型调用 |

Astra 暂不凭空设一个未经讨论的日 token 数值；同样记录实际 token，提供可选 token 上限和独立启用开关，并限制单次上下文。预算只控制新调用准入，不为已开始的调用设置输出截断；允许最后一笔超过 Token 阈值。Sol 的 600 万是输入加输出，缓存输入仍计入，reasoning 若已包含在 output 中不重复累加。美元费用、订阅额度百分比与 token 不能互相冒充。

2026-09-08 独立审阅实际 79 次、1,023,037 token；2026-09-09 查询时 118 次、1,455,864 token，单次中位数约 12,000。以上主要是 Luna 数据，只用于初始预算量级，不能推断 Sol/Astra 的订阅扣费或输出长度相同。

## 当前缺口

`maintenance/infer_worker.rs` 原有单次 Sol fallback，但只匹配允许操作的 `Defer`/归档 `Defer`。`VerifyMaintenance` 不在允许列表，`needs_review` 不触发升级。推理强度目前按操作固定，不能只填一个 Astra deployment 就得到 Low。

`coordinator.rs` 的 Topic correction 循环只处理候选 ID/刷新目标等结构校验错误；语义验证失败没有修正闭环。`max_jobs_per_cycle`、`max_pending_reviews` 与模型超时限制不是升级消费预算。

已有模型验证可能误判：曾有自动刷新声称保留旧主题的主模型语义判断与资产治理边界，但最终正文未保留。因此不能只升级自报不确定的候选，也不能把 verifier 的“已保留”自述当作正文对齐证据。

## 触发与优先级

优先顺序：

1. 将覆盖现有 Topic 的有效刷新候选，即使 Luna 判 `approve`，仍进入 Sol。
2. 全部来源可读、修订仍当前的 `needs_review`，尤其是来源归属、边界遗漏、重复/刷新选择存在分歧。
3. 现有生成阶段的显式 `defer`，继续允许 Sol，但也计入同一预算，不保留一条可绕开预算的旧 fallback。

明确重复/无增量直接收敛。规则检查发现正文为空、ID 不合法、来源已变化等问题，先在本地修正或标 stale，不用强模型猜补。来源无法提供、全文超过证据预算、需要用户补充事实或决定取舍、显式指定人工审核的项直接显示具体原因；不得自动一路升级来换取批准。

Astra 仅在 Sol 已实际完成审阅但仍有可解释的语义分歧时触发。Sol 额度耗尽、不可达、调用超时不构成跳到 Astra 的理由。未解决的问题必须随升级传递，模型需要指出解决了什么，或明确返回未解决。

新 Topic 与关系的自动应用仍服从 `mode`、`auto_apply`、原有积累门槛和当前证据校验；本方案不顺带降低这些门槛。Console 要区分“模型尚未解决”和“模型已通过但应用规则要求人工”，后者不重复消耗升级预算。

## 审阅与修正流程

每层使用明确的审阅合同，返回以下一种结果：通过原候选、无增量、给出修正候选、仍有分歧、缺证据。修正可以修正关系理由、选择保留现有主题、或生成完整的增量合并正文；不能隐式新增来源、任意换目标、转成删除操作或扩大权限。

```text
候选 + Luna 初审
  ├─ 无增量 / 重复 → 记录终态
  ├─ 缺证据 / 已变更 / 必须人工 → 显示原因
  └─ 不确定 / 旧主题刷新 → Sol High
       ├─ 原候选通过 → 应用前校验
       ├─ 修正候选 → 独立 Sol High 复核 → 应用前校验或升级
       └─ 有实质分歧 → Astra Low
            ├─ 原候选通过 → 应用前校验
            ├─ 修正候选 → 独立 Astra Low 复核 → 应用前校验
            └─ 仍未解决 → 人工队列
```

“独立”指新的无共享会话调用，重新读取完整证据，并检验实际候选；不是声称同一个模型的误差相互独立。复核可以看到待解决异议，但不把修正者的自评当事实。每个层级最多一条路径：一次审阅/修正，若产出新正文再一次独立复核；复核失败不在本层循环修补。因而同一证据最多消耗 2 次 Sol、2 次 Astra 调用，全部计入 300/10 的次数上限。普通直接审阅只需一次。网络重试也不得绕过次数或证据路径限制。

主题刷新必须提供旧全文、源全文、候选全文以及实际文本增删。要求解释每项重要删减是无损改写、去重、被新证据否定，还是未解决的信息丢失。没有合法理由的主张/限定删减不得自动通过。文本 diff 只帮助定位，不能以字串存在性替代语义验证。

应用前重新检查来源 Revision、目标当前 Revision、review 状态及候选内容 hash；有变化即 stale，不套用旧批准。自动应用沿用不可变 Revision、新建修订与已有幂等边界。人工已拒绝、接受或正在修改的候选不被迟到的模型回执覆盖。

## 防止重复与并发超支

区分审阅对象和模型调用：

- 审阅对象键：操作、排序后的来源 Page/Revision、目标 Page/Revision、应用语义。仅改标题、空白或候选临时 ID 不产生新额度。
- 对象内部保存初稿与修正稿 hash、明确阶段、实际模型/effort、请求 ID 和所有调用。
- 同证据、同层级已完成或正在执行时，不重复投递。预算等待不会刷新对象身份。跨周期、跨 Console/后台触发、服务重启和自动重试均复用记录。
- 证据更新允许创建新审查；提示词或模型配置变化不自动清空已完成对象。人工“重新审阅”是显式操作，保留理由与原链路，仍受总预算限制。

预算属于 Runtime operational state，与知识 Page 分开。新增窄模块负责预算账本；沿用已有文件锁/原子替换模式，但采用专用预算文件与锁，避免把计数混进维护账本的旧快照合并。每次预占必须在同一个锁区间内重新加载最新状态、检查滚动窗口与对象阶段、写入 reservation 后释放锁；网络调用不持锁。后台与 Console 创建的 operator 均通过此模块，不设独立限额。

每次调用先预占 1 次以及输入字节上界加输出预留量。没有可靠 tokenizer 时使用保守字节上界，不能用中文字符/4 等低估。预算统一采用 `admission` 准入阈值：按实际消耗和预占阻止新调用，已开始的调用正常完成，最后一笔可能超过 Token 阈值。输出预留量仅用于准入估算，不发送为 provider 输出上限。旧配置中的 `hard` 兼容读取为 `admission`，设置页不再提供模式选择。

回执按请求 ID 幂等结算实际 usage，释放多余预占。提交已被接受但 usage 未知时保留预占，重启后查询原请求，不重新发起；取消不等于没有消费。明确提交前失败可释放预占；已经提交的失败调用占用次数。超窗仍未结束的请求继续计入未结预占，不在 24 小时边界凭空释放。完成记录按 UTC 提交时间滚动退出窗口；时钟回拨不提前释放额度。

预算耗尽保留 `waiting_budget`，给出最早可能恢复时间，下一次符合条件时继续；不生成语义拒绝，不重新执行已完成层级。预算文件不可读、损坏或写入失败时停止升级，不能当成空账本；普通只读、检索和已有人工审核继续可用。

## Console

自动维护设置中新增“升级审阅”区域：

- Sol High：启用、部署、effort=high、300 次、600 万 token、24 小时滚动窗口。
- Astra Low：启用、部署、effort=low、10 次，可选 token 上限。
- 显示已结算调用/实际 token、未结预占、剩余可用量、最早释放时间及错误状态。
- 调低预算低于已用量时暂停新调用，保留历史计数；配置保存和重启均不重置预算。

候选卡显示“Luna 初审 → Sol 修正/复核 → Astra 裁决”的已发生步骤、具体升级原因、来源版本、正文变化、usage 和剩余疑点。状态分别为排队、预算等待、执行中、复核中、模型通过但待人工、缺证据、stale、已完成；不能用一个笼统“升级过”布尔值代替。

现有队列可重新纳入调度，但先做证据时效与人工终态检查；上线时不得把历史全部重新跑一遍。优先处理仍有效的未解决项，再处理新写入。

## 代码边界与实施顺序

1. 在 `pcp-runtime/maintenance` 下增加预算状态与审阅调度模块，配置与状态投影增加兼容默认字段；旧数据按无历史消费、仅对启用后的请求扣账迁移，不推测过去消费。
2. `infer_worker.rs` 接受明确 deployment/effort/输出上限与幂等请求身份，现有升级也走统一预占。先验证 Infer Runtime 中 Sol/Astra 实际部署和 effort 能力，缺少部署时报告不可用，不静默换模型。
3. `coordinator.rs` 接入语义修正、独立复核与应用前版本校验。待审路由、模型预算等待和人工终态分离；旧 API 保持可读。
4. Console 接入设置、使用量、步骤与 diff 展示；不复制路由/计费逻辑。
5. 实现后先对保存的真实候选与故障注入场景验证，再备份并启用本地实例。知识数据不硬清理，协议版本不因运行时预算升级而改变。

## 验收

- 两个并发 operator 争抢最后一次/最后一笔 token 时仅一个成功；重复提交和重复结算不双扣。
- 预占后崩溃、提交后断连、usage 未报告、取消、重启、滚动窗口边界、时钟回拨、预算文件损坏均不无限重试或清零额度。
- 同一证据跨调度窗口不再次付费；来源改变令旧批准失效；人工决定优先于迟到自动回执。
- Luna approve 的旧主题刷新仍经过 Sol；needs_review 可升级；Sol 耗尽不跳 Astra；每层修正次数有限。
- 回放真实“前后来源颠倒”“刷新删掉主模型判断边界”“误判研究评测为重复”案例，检查修正后的实际正文，而非仅检查 verdict 标签。
- 所有失败、修正和复核调用计入总预算；缓存输入计数、推理 token 去重及未知 usage 保留正确。
- Console 可见剩余额度、预占与真实阶段；旧 review/ledger 仍能读取；本地重启后同一账本持续生效。

已加入预算并发、重复结算、重启与未知用量、窗口和时钟回拨、账本损坏、分层修正上限、独立复核内容、修订候选身份和人工终态优先等测试。测试证明机制边界，不等于真实模型已纠正历史语义误判。尚未启用本地自动预算调用。

## 配置与兼容

配置位于 `[maintenance.worker.review_budget]`，默认 `enabled = false`。停用后不再运行旧的无预算 Sol fallback；原 `escalation_deployment_id` 仍可解析，但部署选择以预算配置为准，原 `escalation_operations` 继续限制生成阶段的升级操作。账本默认与维护状态文件同目录，文件名为 `maintenance-review-budget.json`；Console 设置不能改变这个账本路径。

默认 Sol 300 次 / 6,000,000 token、Astra 10 次、并发 1、序列化输入上限 512,000 字节，输出预占 8,192 token。调用缓存按证据和阶段持久保留，修正稿 hash 变化不会创建另一条同层路径。有效 Topic / 关系候选中的 `waiting_budget` 与尚未升级的初审不确定项会按每周期一项恢复，复用原稿与已完成初审；历史队列不会整体重新生成。

当前本地 Infer Runtime 运行配置包含 Sol 的命名部署，尚未包含 `codex_gpt_6_astra`。缺少部署或 ACL 时保留具体错误，不替换模型。没有请求身份的未知提交继续占用预占，需要核实 provider 结果，不能通过重启或清空预算伪造退款。


### 待办分流与重复保护（2026-09-09）

Console 根据当前证据和配置将待审事项分为人工决定、自动复核、预算等待、等待积累和自动暂停。模型通过但未达到积累门槛的 Topic 放入可展开的等待区域，不计为人工待办，也不占未解决初审的队列上限。新的短资料组合在调用验证模型前等待积累。上述分流不等于批准或删除候选。

初审模型单独给出的 `requiresUserInput` 不再阻断已启用的有限升级；Sol 须区分普通重复判断与真正缺少作者事实或决定。升级后仍需要用户输入的项保留人工处理。模型步骤是升级事实的来源，不能依赖旧的汇总布尔值。

每轮先检查过期来源、相同证据候选与已存在的关系。同证据候选保留一项；相近标题与来源交叉只作为复核线索，连同待定稿提供给复核模型，不作为自动合并依据。关系的自动写入与人工写入共用决策锁，并在写入前重新检查关系是否已存在、拒绝/抑制决定和来源版本；旧提案对应的关系已存在时直接结清提案。Topic 写入同样在锁内再次检查候选证据身份。
